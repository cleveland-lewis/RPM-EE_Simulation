## **My Understanding of RPM-EE**

**Core Concept:** RPM-EE is a time-stepped, cognitively-motivated simulation that models how an agent (or individual) recursively predicts and adapts to its environment, with a strong emphasis on how **emotional states** (affect, volatility) and **cognitive load** (sensory, working memory, schema stress) modulate this process. It explicitly draws inspiration from **predictive processing / active inference** frameworks.

**Key Variables & Mechanisms:**

1. **Attunement (`attunement_score`)**:
    
    - **Definition**: A latent variable transformed by a sigmoid function into a bounded [0,1] value. It represents a state of **cognitive-emotional readiness, engagement, or alignment** with the environment.
    - **Inputs**: It is positively influenced by `affect` (positive emotions) and negatively influenced by `schema_stress`, `external_load`, `memory_load`, and `affect_volatility`.
    - **Gating**: It can directly `gate_actions` based on its latent value and a `gate_temperature` parameter, suggesting it controls the propensity for active engagement or action execution.
2. **Schema Stress (`schema_stress`)**:
    
    - **Definition**: A bounded [0,1] value that reflects an agent's internal state of **cognitive-emotional strain**.
    - **Components**: It blends two key components:
        - **Slow Drive**: Reflects persistent `internal_load` (working memory occupancy) and `external_load`.
        - **Fast Surprisal**: Reflects prediction error (`abs(ext_load - e_ema)`) on external sensory input.
    - **Dynamics**: It has a `stress_decay` parameter, allowing it to dissipate over time, and its computation involves an Exponential Moving Average (`tau`).
    - **Cognitive Rationale**: Rises with sustained cognitive effort/load and unexpected (unpredicted) events, aligning with predictive processing notions of "precision" and "surprise."
3. **Recursivity**:
    
    - Primarily **temporal**: The current state of `stress_latent` is influenced by `stress_prev` (the previous tick's stress).
    - **Feedback loops**: Elements like `e_ema` (EMA of external load) and `ema_aff` (EMA of affect) continuously update and feed into subsequent calculations of prediction error, volatility, and stress.
    - `dynamic_prune` (memory pruning threshold) is also tied to `stress_prev`, showing how internal states influence cognitive resource management.
4. **Emotional Encoding**:
    
    - **Direct**: `avg_affect_feedback` (mean valence of emotions, -1 to 1) and `affect_volatility` (short-term variability of emotions) are explicit inputs to the attunement equation.
    - **Indirect**: These emotional states also influence the `SimulationClusterArbiter`'s decision-making process for `replay_mode` selection, impacting how the system chooses to "Explore," "Converge," or "Stabilize" its internal models.
5. **Relation to Existing Models**:
    
    - Strongly aligned with **Predictive Processing / Active Inference**. The terminology (`precision`, `prediction error`, `surprisal`, `attunement` as a form of precision/certainty in a policy, `expected free energy` in the arbiter) explicitly points to this.
    - The "learning edition" comments emphasize its pedagogical role in teaching these concepts.

# Potential Issues to be Added:
## **Issues for RPM-EE Project**

### **1. Core Simulation Logic & Parameter Management**

- **Issue: Modality Input Generation (Smell/Taste always zero)**
    
    - **Description**: The `_generate_base_arrays` functions (both JAX and NumPy) currently produce `smell` and `taste` arrays that are always zero. The comment "smell and taste are zeros in current generator; omit or include with max=1 to keep flexible" suggests this is intentional for now. However, if these modalities are intended to contribute to `external_load` or other dynamics in the future, this needs to be explicitly addressed.
    - **Impact**: Limits the current scope of sensory input and might lead to incorrect assumptions about modality contributions.
    - **Suggested Fix/Future Work**: Implement meaningful (e.g., random, patterned) generation for `smell` and `taste` arrays, or remove them if they are not planned for the model.
- **Issue: Inconsistent Random Seed Handling**
    
    - **Description**: In `run_simulation`, both `random.seed(int(seed))` and `np.random.seed(int(seed))` are called. Later, `_generate_base_arrays` uses `np.random.default_rng(seed)` (for NumPy path) or `jax_random.PRNGKey(int(seed))` (for JAX path). Using multiple seeding methods for different random number generators can lead to subtle non-reproducibility issues, especially if `random` or `np.random.seed` are called globally and then overridden or mixed with `default_rng`.
    - **Impact**: Potential for runs to not be perfectly reproducible, making debugging and scientific validation harder.
    - **Suggested Fix**: Standardize on a single, modern random number generation approach (e.g., exclusively use `np.random.default_rng(seed)` and pass this `rng` object to all functions that require randomness, or ensure JAX's PRNGKey is consistently managed). Remove redundant seeding calls.
- **Issue: `SimulationClusterArbiter` Instantiation within Loop**
    
    - **Description**: The `SimulationClusterArbiter` object (`_arb`) is instantiated inside the `for i in range(total_ticks):` loop within `run_simulation`. If this class holds any internal state (e.g., adaptive parameters from `adaptive=True`), re-instantiating it every tick might reset this state, leading to unexpected behavior or incorrect simulation dynamics.
    - **Impact**: The arbiter's "adaptive" behavior might not function as intended, or it might consume unnecessary computational resources.
    - **Suggested Fix**: Move the `_arb = SimulationClusterArbiter(...)` instantiation _before_ the main simulation loop, unless there's a specific theoretical reason for it to be re-initialized per tick (which should be clearly documented).
- **Issue: Global Module-Level Override in `fit_nc_mcm`**
    
    - **Description**: The `fit_nc_mcm` function modifies a global module-level variable: `_mcm._SIM_OVERRIDES = dict(sim_overrides)`. This practice can lead to non-deterministic behavior and difficult-to-trace bugs, especially when `fit_nc_mcm` is called multiple times or in parallel (e.g., with `workers` > 1).
    - **Impact**: Reduced reproducibility, particularly in batch processing or parallel computing environments, and makes reasoning about module state difficult.
    - **Suggested Fix**: Refactor `nc_mcm_model` to accept `sim_overrides` as an explicit argument to its functions (e.g., `run_multiple_simulations`) rather than relying on a global side effect. This promotes cleaner, more predictable code.
- **Issue: `within_stratum_theta0_jitter` Application Logic**
    
    - **Description**: The `within_stratum_theta0_jitter` parameter is applied directly to `theta0` _after_ presets are loaded, with a local `np.random.normal` call. This creates a jitter on a parameter that might already be defined by a preset, and its interaction with the `seed` (or lack thereof) needs careful consideration for reproducibility within and across stratified runs.
    - **Impact**: Can introduce unintended variability or make it hard to track the true `theta0` value being used for a given simulation run.
    - **Suggested Fix**: Clearly define if `jitter` is a property of the _preset_ or a _run-time modification_. If it's a run-time modification, ensure it's applied consistently and predictably, and consider if it should be an explicit parameter within each preset's definition (`theta0_jitter_scale`) rather than a top-level `run_simulation` override.
